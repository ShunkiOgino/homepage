Memory usage ballooned to 50.6GB, putting severe pressure on the swap space.

When running multiple AIs side-by-side in a local environment, a design that minimizes resource monopolization is essential. Normally, one might think that using the service management functions of a package manager (such as brew services) would allow for proper control over process startup and shutdown, enabling efficient memory rotation. Since you can delegate background processing with a single command, it seems like the optimal solution.

However, in reality, there was a pitfall. While running ComfyUI (an image generation AI tool) and oMLX (the local AI execution environment I use) together, the evacuation mechanism intended to free up resources was calling brew services, but oMLX was rejecting that management. As a result, the control commands became silent no-ops (misfires), and because the processes persisted, memory usage expanded.

To resolve this "control misfire," I rewrote my management method. Instead of going through an abstract service management layer, I migrated directly to OS-level process management using launchctl's bootstrap and bootout. Furthermore, I eliminated the expectation that "it should have stopped because I sent the command" and introduced a mechanism to determine if the process was actually running by checking the availability of port 8080. By performing operational determination based on the objective fact of the physical port status, I ensured that processes were terminated reliably. By changing to this design, memory usage was reduced from 50.6GB to 32.3GB.

What is important here is the practice of cross-referencing and confirming the physical trace—"did port 8080 actually open?"—every time a stop instruction is issued. In systems dealing with massive resources like AI models, there is always a risk that processes will silently misfire due to the specifications of management tools or rejection from the model side. Strict management at the OS level combined with the back-and-forth motion of verifying the actual state via port monitoring. By combining this effective determination, you can avoid crashes and swap pressure caused by resource contention.
