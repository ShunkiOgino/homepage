I eliminated GUIs from my streaming environment, switching to a configuration driven by `python broadcast.py` combining headless Chromium and ffmpeg. This is because GUI tools like OBS are difficult for AI to operate.

I have touched upon "GUI elimination" before, but this time I am diving into the implementation of specific control infrastructure, such as `broadcast.py`, JSON scripts via Playwright, and `token_health.py`.

Most people feel that having a GUI tool they can operate visually is "convenient." However, when you try to entrust operations to an AI, that GUI becomes an opaque wall. The effort required to make an AI recognize coordinates or elements on a screen and click them accurately is far too costly compared to controlling things directly via APIs or code. There is a paradox where ease of use for humans becomes a bottleneck for automation.

What I built is an environment where everything is completed on a code base, allowing the AI to control it autonomously.

Take the creation of demo videos, for example. Instead of manually screen recording, I implemented a system that automatically records UI operations from a JSON script using Playwright (a browser automation library) and ffmpeg. I defined operations in a step-driven format—"goto/click/type/scroll/wait/caption"—automating everything from server startup to video output. I encountered an issue where SVG nodes (vector drawing elements) could not be clicked, but I solved this by using coordinate-based clicking. By doing this, I eliminated the manual labor of replacing assets and maintained a state where videos can be generated via code.

Furthermore, to maintain autonomous operation, "health monitoring" is indispensable. I created `token_health.py` to detect the expiration of tokens (authentication keys) for services like YouTube and Gmail and send notifications via Telegram. I have configured this to run every Monday at 5:00 AM using launchd (the Mac task scheduler). Without a "mechanism to notice when things have died," automation becomes nothing more than a source of anxiety.

At the root of this design is a preference for "fixability."

If you use black-box tools, you have no choice but to wait for the provider's fix when a bug appears. However, if you compose your system from components like OSS and custom scripts, you can isolate the specific point of failure and improve it yourself. For example, while game_orbit is already implemented for self-running, reign lacks a self-running demo implementation on the HTML side and results in a still image; I can take an approach to fix this via code. Rather than using infrastructure as "given tools," I maintain it as a "describable structure." I believe this is the optimal solution for control in the AI era.

Is the tool you rely on right now structured in a way that allows you to fix it with your own hands when something goes wrong? Or are you conforming to the convenience of a GUI someone else created?
